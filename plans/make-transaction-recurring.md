# Create Recurring Schedule from a Transaction

## Product Principle

> **Creating a recurring schedule should feel like creating a template, not
> converting an existing transaction.**

That sentence guides every decision below — wording, helpers, and the
architecture independence rule.

---

## What this is (and isn't)

- **Is:** a kebab action on a Transaction row that opens the existing
  RecurringForm pre-filled from that transaction, creating a **new**
  recurring schedule.
- **Isn't:** converting or modifying the original transaction. The source
  transaction is never touched.

### Architecture independence (future-proofing)

A recurring schedule is **independent** of the source transaction after
creation:
- Editing the recurring schedule never modifies the original transaction.
- Editing the original transaction never updates the recurring schedule.

**Generated transactions are snapshots.** Future edits to the recurring
schedule only affect *future* generated transactions; previously generated
transactions remain unchanged. Never retroactively modify historical
transactions.

No synchronization. Ever. This is a deliberate product rule so future
developers don't try to keep the two linked.

## Entry point

- **Hover cluster unchanged:** `[edit, duplicate] | divider | [delete]` on
  Transactions. No change.
- **Kebab:** add a new item **Create recurring schedule** (repeat icon), fed
  by a new optional `onMakeRecurring` prop in the shared `actions` array in
  `RowActionsMenu.svelte` (after Duplicate, before Delete). Because the array
  is shared, the item appears in both the desktop popover and the mobile sheet
  automatically.

### Prop shape

`onMakeRecurring(transaction: Transaction)` — pass the **whole transaction**,
not an id, so the page has description / amount / category / type / date
without re-looking-up the row.

---

## Flow

1. User opens the kebab → **Create recurring schedule**.
2. `TransactionList` forwards `onMakeRecurring(txn)` to the Transactions page.
3. The page opens a `SlideOver` titled **Create Recurring Schedule** hosting
   `RecurringForm` in fetch mode (`onSubmit` → POST `/api/recurring` with the
   same `RecurringInput` body the `/recurring` slide panel sends).
4. The form is pre-filled from the transaction (mapping + start-date
   semantics below). The original transaction is left untouched — we only
   `INSERT` a new `recurring_transactions` row.
5. On success: close the panel, toast **"Recurring schedule created. Future
   transactions will be generated automatically."** with an **Open Recurring**
   link → `/recurring`.

## Start date semantics (the one real functional gap — now defined)

The scheduler computes `next_run = start_date + 1 interval`
([recurringService.ts:94](src/lib/server/recurringService.ts#L94) +
[recurring.ts:28](src/lib/utils/recurring.ts#L28)), i.e. the first
**generated** transaction is one cadence point *after* the anchor date. So:

```
start_date = max(today, txn.date)
next_run   = start_date + 1 interval   ← shown in the "Next scheduled transaction" card
```

- **Recent transaction** (e.g., Jul 18, today Aug 6): `start_date = Jul 18`
  → `next_run = Aug 18`. First generated transaction is the next occurrence
  after the source. No double-count (the source date itself is never
  generated), no skipped month.
- **Old transaction** (e.g., 2021, today 2026): the anchor clamps to today →
  `start_date = today` → `next_run = today + 1 month`. **The scheduler never
  backfills a wall of missed transactions.** The cadence restarts fresh from
  today.
- Clamped schedules anchor their day-of-month to *today's* day (v1). If we
  ever want to preserve the source's day-of-month (e.g. always the 18th), that
  requires exposing `day_of_month` — flagged as v2.

The **Next scheduled transaction** card displays the first transaction that
will actually be generated by the scheduler — it matches the scheduler's
computed `next_run`. The scheduler is the authority; the card only renders
what it computed.

### Pre-fill mapping

| Recurring field | Source |
|---|---|
| `type` | `txn.type` (income/expense maps 1:1) |
| `amount` | `Math.abs(txn.amount)` (amount is stored positive; abs is a safety net) |
| `description` | `txn.description` |
| `category_id` | `txn.category_id` (categories are shared between the tables) |
| `frequency` | `'monthly'` (v1 default) |
| `interval` | `1` |
| `start_date` | `max(today, txn.date)` — see start-date semantics above |
| `end_date` | `''` (never ends) |
| `active` | `true` |

## Cancel with dirty-check

- `RecurringForm` exposes a `bindable dirty` signal (or `ondirty` callback) —
  true when any field differs from its seeded values.
- The Transactions page tracks it. On close (✕ or Cancel):
  - **Untouched** → close silently.
  - **Dirty** → confirm dialog: **"Discard recurring schedule?"** (Keep
    editing / Discard).
- `RecurringForm` also gains an optional `onCancel` prop. In slide-panel mode
  the Cancel button must call `onCancel` (→ the page's dirty-check) instead of
  the hardcoded `goto('/recurring')` ([RecurringForm.svelte:313](src/lib/components/RecurringForm.svelte#L313)), which would otherwise bounce the user off the Transactions page.

## Edge cases

- **Transfer / neutral transactions:** schema has only `income`/`expense` — no
  transfer type exists, so nothing to exclude; every transaction maps.
- **Missing category:** impossible at rest (`category_id` NOT NULL + RESTRICT);
  RecurringForm also self-heals if a category ever drops out of the filtered
  list.
- **Old transaction:** start date clamps to today — no historical backfill
  (see start-date semantics).
- **Paid vs active:** transactions have no status — N/A. Recurring defaults
  `active = true`.
- **After save:** panel closes, toast fires with **Open Recurring** →
  `/recurring`.

## v2 roadmap (deliberately not built now)

- **Duplicate guard ("Edit recurring" on generated rows):** transactions carry
  no `recurring_id` today, and generated transactions insert without a link.
  Until generated transactions exist to guard against, there's nothing to
  detect. Deferred; requires a migration (`recurring_id` FK on transactions +
  set on generate + backfill).
- **Smart frequency inference:** infer `weekly` when a transaction recurs on
  the same weekday (Fridays, Mondays, …). Monthly is the correct v1 default.
- **Cadence suggestion** from similar past transactions (same category +
  description).
- **Preserve source day-of-month on clamp:** expose `day_of_month` so an old
  transaction's cadence keeps its original day instead of anchoring to today.
